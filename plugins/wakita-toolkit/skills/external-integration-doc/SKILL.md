# 对外接口对接文档写作

## 定位：契约交付物，不是 spec

- **spec** 是内部工作文档：可以写实现史、待定项、组件拆分、拍板号。
- **对接文档** 是给外部读者（对接方、技术主管、领导）的契约：读者照它就能调通。
- 读者认知起点是零：不知道什么已建好、什么在开发、内部怎么实现。

## 结构：四件事 + 步骤

1. **能调什么**：接口清单 + 地址（全路径，或定死公共前缀并给拼接示例）。
2. **怎么调**：方法、参数形态（查询参数还是 JSON 正文）、鉴权头、完整请求/响应示例
   （逐字段注释含义）。
3. **调完得到什么**：返回语义、错误形态、边界行为（预检/兜底/超时）。
4. **先做什么后做什么**：编号对接步骤，第一步必须是读者当下就能动手的。

## 三禁

- **禁内部行话**：已做好/新建/组件/壳/拍板号/复用与新建之争——全部不出现。
  行为解释只用读者视角（「大屏每 2 秒自查状态」而不是「壳页面轮询」）。
- **禁开发状态叙事**：不交代实现史；接口新旧以部署事实为准——新增但已部署写
  「当前可用」，未实现的一律不写进步骤。
- **禁空头承诺**：「现在就能开始」落笔前，接口必须真实存在并被调通过，
  否则对接方一调就穿帮。

## 事实核对（凭记忆写签名必错）

每个接口逐条打开后端真实代码核对：

- 方法 / 路径 / 参数形态（查询参数 vs JSON 正文）
- 鉴权头与权限要求
- 成功状态码与响应包络（是 `code=200` 还是 `code=0`）
- 错误形态（4xx/5xx 的 detail 结构）
- 事件序列（SSE：谁先发、谁结束、超时行为）
- 分页/限额参数的真实名字（`top_k` 不是 `page/page_size`）

补充规则：

- SSE 接口注明「用 fetch 读流，`EventSource` 带不了鉴权头」。
- 拿不准新旧归类：查 git 与生产 OpenAPI，别猜。
- Swagger 里的 JSON 请求体枚举**不渲染下拉框**；枚举可见位置是 Schema 的
  「Available values」和 Try it out 的校验报错。别承诺「下拉框」。

## 交付前检查清单

- [ ] 每个接口的方法/路径/参数形态/鉴权/返回码都对照真实代码核对过
- [ ] 请求与响应示例可直接复制执行（含鉴权头与完整 URL）
- [ ] 错误码与错误体示例已列出
- [ ] 步骤编号中没有任何未实现/未部署的接口
- [ ] 全文没有内部文件名、组件名、拍板号、开发状态
- [ ] 已实际调通至少一条主链路（或拿到他人调通证据）

## 反模式

- ❌ 把内部 spec 删掉几段直接当对接文档发出去
- ❌ 写「支持分页」但实际接口只有 `top_k`
- ❌ 写「请求体 JSON」但真实接口要查询参数
- ❌ 承诺「现在就能开始」而接口还在开发分支
