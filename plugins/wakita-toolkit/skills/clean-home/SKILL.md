# 清理房间（clean-home）

你现在被要求做一次「清理房间」审查。把用户指定的模块当成一间房间：先看整体乱在哪，再按区域逐项检查，最后给出清理顺序。

<role>
你是审查编排者，不是规则执行者。本 skill 只规定：按什么顺序、为了什么目的、去加载哪个领域 skill。具体判定标准以被加载的 skill 为准，不要在这里即兴发明检查项。
</role>

## 怎么执行

1. **先复述房间范围**：用一句话说明你要审哪些目录/文件、是「全量体检」还是「聚焦清理」、对应的 spec 在哪里。范围不清就先问，不要扩散到无关区域。
2. **按步骤走**：每一步先写清「这一步要回答什么问题」，再加载对应 skill。固定格式：
   `[step N] 目的：<一句话>；加载：<skill 名>`
3. **加载失败不猜**：skill 不存在、被禁用、内容读不到，记入「证据缺失」，继续下一步；不要把缺失当成通过。
4. **默认只出报告**：不改代码。用户明确说「按报告修」才进入修复，且一次只处理一个优先级批次。
5. **最后自检**：报告末尾列出「已加载 skill / 未加载 skill / 证据缺口」。没有这一节不算完成。

## 审查步骤

### Step 0 界定房间
**这一步要做什么**：确认审查范围、模式和 spec 基线，避免审错对象或扩散。
**加载**：无。读用户指定目录 + `docs/specs/` 下对应 spec + 项目 `AGENTS.md`。
**产出**：范围一句话、模式（全量/聚焦）、spec 路径或「无 spec，按需求描述审查」。

### Step 1 对齐：这间房是按图纸盖的吗
**这一步要做什么**：对照 spec/需求，查实现有没有偏离、AI 有没有在没依据处猜假设、有没有擅自扩范围或删需求。
**加载**：`spec-alignment-review`。
**产出**：偏离项、未记录假设、范围蔓延，每条带证据。

### Step 2 契约：前后端和数据库说的是同一件事吗
**这一步要做什么**：查接口、类型、字段、错误码、组件 props、DB/ORM/DTO 是否同源，有没有双轨或漂移。
**加载**：`robust-architecture`，按其 API 信封、单一真源、DB 规约章节。
**产出**：契约漂移、隐式约定、数据层不一致。

### Step 3 安全：有没有不该敞开的门窗
**这一步要做什么**：查密钥、依赖、敏感模块、常规漏洞。
**加载**：`project-compliance-check`，按其安全合规章节。
**产出**：可利用风险、失控的敏感模块、不可信依赖。

### Step 4 验证：有没有真跑过、真测过
**这一步要做什么**：查核心逻辑有没有测试、关键路径有没有集成/E2E、AI 有没有用 stub、快乐路径或幻觉 API 冒充完成。
**加载**：`test-quality-principles` + `ai-code-failure-modes`。
**产出**：测试缺口、假绿证据、AI 特有失败模式。

### Step 5 结构：房间里的东西摆得能不能住
**这一步要做什么**：查硬编码、重复造轮子、超长文件/函数、跨层调用、循环依赖、命名与职责混乱。
**加载**：`code-structure-metrics`（硬编码/超长/理解困难/耦合）+ `code-reuse-audit`（未复用/重复与分叉）；分层违规（E4）回 `robust-architecture`。
**产出**：混乱地图 Top 5，每个信号至少一条量化证据。

### Step 6 按需：地基和出口有没有问题
**这一步要做什么**：涉及数据库迁移、部署、容器时，补查可回滚性、迁移幂等、部署验证。
**加载**：按实际情况选择 `idempotent-migration` / `cd-deploy-verification` / `docker-compose-prod-default`。不涉及就跳过，并在报告里说明「本步不适用」。
**产出**：不可回滚项、迁移锁窗风险、部署验证缺口。

### Step 7 汇总：给出清理顺序
**这一步要做什么**：把各步发现合并去重，按紧急度排序，给三档结论。
**加载**：无。按下方「报告契约」输出。
**产出**：一份可执行的清理报告。

## 报告契约

### 级别合成
- **P0 立即处理**：继续开发会失控，或存在泄露/越权风险。例：核心逻辑 stub 冒充、契约双轨、不可回滚、密钥硬编码、敏感模块无人把关。
- **P1 本迭代清理**：明显拖慢后续开发。例：重复造轮子、跨层调用、超长函数、配置/文案硬编码。
- **P2 记录技术债**：不影响当前正确性，但会增加未来成本。例：命名不达意、注释缺失、小重复、可提取常量。
- 多个 skill 对同一问题给出不同级别时取高；领域 skill 有更具体定义时以它为准。

### 证据
每条必须有 `文件:行` / 函数 / 调用链。没有证据的写「证据缺失」，不进 P0/P1。

### 三档结论
- **可继续开发**：无 P0，P1 少量。
- **建议先局部清理再继续**：有 P0 或 P1 集中在少数文件，清理成本可控。
- **建议重构后再继续**：P0 多处、混乱信号密集、跨层耦合成网。

## 禁止事项

- 不要跳过步骤。不要因为测试通过就跳过结构问题。
- 不要只读目录名就判断分层，要看实际 import 和调用链。
- 不要用「结构较乱」「建议优化」这类无证据结论。
- 不要给出「全部重写」作为首选建议，除非证据支持且说明代价。
- 不要擅自改代码或扩大审查范围。
- 不要在报告里复述领域 skill 的规则全文，只写结论和证据。

## 适用边界

- 本 skill 的「房间」指代码模块，不涉及文件系统或 home 目录清理。
- 本 skill 是编排入口，不替代任何领域 skill。领域规则以被加载的 skill 为准。
- 聚焦清理模式只查结构相关步骤（Step 5 + 硬编码/复用/分层），跳过完整安全与测试深查，并在报告开头注明未覆盖项。
- 默认只出报告；修复由用户明确要求后另起流程，一次一个优先级批次。
