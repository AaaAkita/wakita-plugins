# 中文技术表达规范

## 何时触发

- 写 `docs/specs/` 下的 spec 或方案文档
- 向用户汇报排障结论、故障原因、修复方案
- 前端要展示 API/表单错误提示
- 写代码注释（尤其安全、数据一致性、单位/坐标系、降级兼容逻辑）

## 一、Spec：业务语言先行，技术细节后置

**正文用业务语言按因果/时序讲清楚：**

1. 这个功能服务谁、解决什么问题
2. 数据/状态怎么流动，每个状态是什么意思
3. 规则与公式（用具体数字举正反例，如「87 条里只有 18 条该处理，所以分母是 18」）
4. 为什么选这个方案、放弃哪个

**变量名、字段名、`file:line` 集中收进末尾「技术要点」小节**，正文只在必要处点名。

完稿自检：**不懂代码的人只看正文，能不能说出「为什么这么改」？**

反例：正文全是 SQL 条件、字段名、行号，读者要先在心里还原业务事实才能看懂，
等于没写。

## 二、排障汇报：序号白话，结论先行

- 结论先给，再给证据；不要从排查过程讲起
- 用序号分点，一条一件事
- **结论里禁止堆英文变量名/字段名**；必须提时写成「中文名（`field_name`）」
- 严格区分「事实（实读数据/日志/代码）」与「推断」，推断要标注
- 每条结论附可复核的命令、文件:行号或数据，不写「应该」「可能已经好了」
- 修复类汇报必须包含：根因、改了什么、怎么验证、还有什么风险

## 三、用户可见错误提示：中文映射

- 前端所有 API/表单错误必须显示中文，不原样弹后端英文 `detail`
- 按 HTTP 状态码 + 已知 detail 建中文映射；未知英文 detail 用状态码文案兜底
- 原始 detail 只允许 `console.warn` 在开发环境
- 文案要说人话并给出下一步，例如：
  - 404 →「请求的接口不存在，请确认版本或联系管理员」
  - 409 →「该记录已存在，请勿重复提交」
  - 422 →「输入格式不正确，请检查后重试」
  - 网络失败 →「无法连接服务器，请确认后端已启动」
- 技术术语只保留用户能理解的（如「登录已过期」），不出现异常类名、堆栈

## 四、代码注释：解释 why，不解释 what

- 模块/关键函数加简短说明
- 重点写明：非显而易见的决策、约束、安全不变量、单位/坐标系、降级与兼容策略
- 不为显而易见的赋值、循环写废话注释
- 注释也写中文；行业缩写（JWT/SSE/DPI 等）保持原文

```python
# ✅ 说明约束：FULLTEXT 表 ADD COLUMN 无法 INSTANT，必须整表 COPY
# ❌ 说明动作：给表加一列
```

## 五、通用原则

- 面向人的文本（spec/汇报/错误/注释）优先中文；代码标识符、协议名、命令保持原文
- 一个概念只用一个中文叫法，不混用「任务/作业」「条目/记录」
- 数字带单位；时间带时区或明确「本地时间」
- 不写「整体很好」「基本没问题」这类空话，直接给结论与风险

## 检查清单

- [ ] spec 正文能否被非开发读者理解
- [ ] 排障汇报是否结论先行、序号分点、事实/推断分离
- [ ] 结论中的英文变量名是否已中文化或加中文说明
- [ ] 前端错误是否全部中文映射，原始 detail 是否只在 dev console
- [ ] 注释是否解释了 why/约束，而不是复述代码
- [ ] 是否避免了空话与模糊表述
