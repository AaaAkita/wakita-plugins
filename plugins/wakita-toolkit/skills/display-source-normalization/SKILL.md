# 多源展示规范化（Display Source Normalization）

核心命题：**同一业务对象只允许一个展示模型。** 来源差异（字段名、兜底、伪数据、脱敏）
全部收敛在适配器里，渲染层不感知来源。

## 何时触发

满足任一条件就必须按本 skill 走：

- 同一 UI 组件消费两个及以上数据来源（DB 列表 / 实时 SSE / 缓存 / 旁路流水 / 历史回放）
- 同一业务对象在两条链路上字段名或兜底规则不同（snake_case vs camelCase、`or 0`、截断标题）
- 修过「有的数据显示 A、有的显示 B」类不一致 bug——修完要补规范化，不是再写一个特判
- 审查前端展示层，发现渲染组件里出现来源分支

## 三层结构（缺一不可）

```
源 A ─┐
源 B ─┼─→ 适配器（每源一个）─→ 展示模型 ─→ 唯一的渲染规则
源 C ─┘        ↑ 清洗/翻译          ↑ 只描述展示需要什么
```

1. **展示模型**（如 `types/display.ts`）：只保留渲染需要的字段，命名统一，缺失一律 `null`。
2. **适配器**（如 `utils/display-normalize.ts`）：每源一个函数，把源格式翻译成模型。
   伪数据识别（兜底标题、假置信度）、平台特判、脱敏全部在这里。
3. **渲染层**：只读展示模型。禁止来源分支（`if (source === 'live')`）、
   字段名兼容（`item.risk_level ?? item.riskLevel`）、二次兜底。

## 硬规则

- **缺失 = null**：不许用 `0`、空串、`"无"` 冒充。源端丢失的 null 语义在适配器里恢复并注释。
- **清洗在适配层，格式化在渲染层**：字符截断、时间格式化、颜色、字号不进模型。
- **脱敏在适配层**：真实昵称等敏感字段在输出到 DOM 前统一处理；内部标记不进视觉层。
- **来源标记只用于逻辑**：`source`（live/history/db）只参与去重、排序、填充队列，
  不得改变样式或文案（演示场景尤其如此）。
- **去重按来源分域**：实时流防重投用独立集合；历史回放/垫底不得占用它，
  否则同一行被重新处理时会被误杀。
- **兜底值必须可识别**：列表接口可能把空标题兜底成「摘要前 40 字 + ...」，
  适配器要按形态识别伪标题，不能假定「有 title 就是真标题」。
- **后端字段命名先数分布再改名**：全量 OpenAPI 统计 snake_case / camelCase 占比，
  跟随主流；历史例外由适配器兼容。已冻结的对外载荷不动。

## 开发清单

- [ ] 列出全部来源与各自字段表，标出同名不同拼法、兜底差异、缺失语义
- [ ] 定义展示模型（字段 + null 语义注释）
- [ ] 为每源写适配器，把伪数据识别规则写进适配器并注明来源
- [ ] 渲染层改为只读模型；grep 确认没有来源分支/字段兼容残留
- [ ] 写「双源等价」单测：同一业务数据从两个源进来，除 `source` 外逐字段相等
- [ ] 写伪数据用例（兜底标题、未分析置信度、空时间）
- [ ] 后端字段改名/新增走全量测试（响应结构锁测试会拦）

## 审查清单（auditor 用）

- [ ] 渲染层是否存在 `??` 字段兼容、`source` 分支、平台特判？→ 一律报
- [ ] 适配器是否伪造了缺失值（`or 0`、`|| '无'`）？→ 报
- [ ] 两个适配器对同一字段的清洗规则是否一致？→ 不一致报
- [ ] 双源等价单测是否存在？没有 → 报
- [ ] 改动是否影响已冻结的对外载荷（进度事件、公开响应键序）？→ 跑全量测试

## 反模式

- ❌ 在渲染层写 `item.risk_level ?? item.riskLevel` —— 兼容逻辑散落在视图里
- ❌ 实时流和历史回放各写一套格式化 —— 迟早出现两种日期/标题/颜色
- ❌ 用兜底值当真实值展示 —— 用户看到的是编造出来的标题
- ❌ 为了「看起来一致」在渲染层猜来源 —— 来源判断应在适配器完成

## 真实案例（脱敏）

历史回放卡片有标题、实时流卡片没有。根因：列表接口对空 title 用「摘要前 40 字 + ...」
兜底，历史适配器把兜底值当成真标题。处置：`normalizeTitle()` 统一剔除伪标题，
两个适配器产出同一 `DisplayItem`；历史回放不再写入实时去重集合。
