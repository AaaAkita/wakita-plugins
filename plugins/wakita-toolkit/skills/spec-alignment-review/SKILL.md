# Spec 对齐审查

判断一份实现是不是按图纸盖的：spec/需求说了什么，代码做了什么，两者差在哪。只回答对齐问题，不替代契约、安全、结构审查。

## 输入

审查前尽量收集：

- spec 路径（优先 `docs/specs/` 下状态为「待实现」或「开发完成」的文件）或用户原始需求描述。
- 项目规则：`AGENTS.md`、`CLAUDE.md`、编码规范、目录职责说明。
- 实现证据：diff、提交记录、关键入口文件。
- 如果 spec 不存在：明确写「无 spec，按用户需求描述审查」，不要自己补一份 spec 当依据。

## 检查清单

| ID | 检查项 | 怎么判 | 级别建议 |
|---|---|---|---|
| A1 | 对照 spec | 实现是否覆盖 spec 的功能点？有没有 AI 自行扩展、删减或改变语义的需求？ | 核心偏离 P0，轻微 P1 |
| A2 | 假设显式化 | AI 在没依据的地方做的假设，是否被记录或向用户确认？ | 影响接口/数据结构 P0，其他 P1 |
| A3 | 遵守项目规则 | 技术栈、目录职责、命名、异常处理、响应体是否符合 `AGENTS.md`/项目规范？ | 违反硬规则 P1，引入禁用依赖 P0 |
| A4 | 范围克制 | 有没有「顺手」改无关模块、大范围格式化、无关重命名？ | 无关改动占比高 P1 |

## 执行方法

1. 先读 spec 的「摘要 / 方案 / 技术要点 / 关键约束」，列出可验证的功能点和约束。
2. 再读实现入口和 diff，把每个功能点映射到具体文件/函数。
3. 对不上号的，分三类记录：
   - **漏实现**：spec 有、代码没有。
   - **擅自扩展**：spec 没有、代码加了。
   - **语义偏离**：有实现，但行为与 spec 不同。
4. 对 AI 的假设，找记录：spec 备注、代码注释、提交信息、用户确认。找不到记录的，标「未记录假设」。
5. 无关改动用 diff 统计：格式化、重命名、依赖升级是否混进本次范围。

## 输出

每条发现给：

- ID（A1-A4）
- 问题一句话
- 证据：`文件:行` / 函数 / diff 片段 / spec 对应段落
- 建议级别（P0/P1/P2，仅建议，最终由 clean-home 汇总时合成）

最后给一句总结：实现与 spec 是「一致 / 有轻微偏差 / 有核心偏离」，并列出证据缺口（如 spec 缺失、需求只有口头描述）。

## 边界

- 契约漂移（类型/字段/错误码/组件 props/DB/ORM/DTO）→ `robust-architecture`。
- 安全、依赖、敏感模块 → `project-compliance-check`。
- 测试是否存在、AI 特有失败 → `test-quality-principles` / `ai-code-failure-modes`。
- 代码结构、重复、分层 → `code-structure-metrics` / `code-reuse-audit` / `robust-architecture`。
- 本 skill 只审「有没有按 spec/需求做、有没有多做/少做/乱做」，不审「做得好不好」。
